# 🧬 Algorithm History / 算法进化史

这个文件记录 Mini Metro AI Lab 中**所有进入正式实验的算法**，包括最终冠军、阶段性冠军、失败方案和被淘汰方案。

目标不是只留下“最后赢的人”，而是保留完整的工程与研究记忆，避免未来重复走已经验证过的死路，也方便理解冠军策略是怎样一步步演化出来的。

## 记录原则

每个进入 Arena 的算法都必须留下以下信息：

- 算法名称与版本
- 实现提交 / PR
- 核心思路
- 关键参数
- 对战基线
- 固定 Seeds 与模拟预算
- Simulation Protocol 版本
- Benchmark Scenario 版本
- 平均运送量
- 中位数
- 最低 / 最高运送量
- Game Over 率
- 候车与拥堵健康指标
- 无效动作数量 / 比例
- 主要优点
- 主要缺点
- 失败案例 / 典型崩局模式
- 最终状态
- 淘汰原因或晋级原因
- 是否值得未来复活

## 状态定义

| 状态 | 含义 |
| --- | --- |
| `baseline` | 当前基准算法 |
| `candidate` | 正在实验或调参 |
| `champion` | 当前默认冠军 |
| `retired` | 曾经有效，但已被更强方案替代 |
| `eliminated` | 经公平对战后淘汰 |
| `archived` | 保留研究价值，但暂不继续投入 |

## 实验纪律

1. **不删除失败算法的历史。** 代码可以移出默认路径，但实验记录必须保留。
2. **不只记录分数。** 还要写清楚它为什么赢、为什么输，以及在哪类局面下会崩。
3. **同一轮比较必须使用相同 Seeds、步长、时间预算、场景和 Simulation Protocol。**
4. **任何“新冠军”必须在 Arena 中明确击败当前冠军。**
5. **小样本结果只算候选证据。** 真正晋级前要扩大 Seeds 数量，并观察最差局表现。
6. **被淘汰不等于没价值。** 某些算法可能适合作为搜索启发、局部策略、Value 特征或应急控制器。
7. **协议升级不改写历史。** 旧结果保留原协议标签；需要新口径时重新跑并追加记录。
8. **场景升级也不偷换赛道。** Classic、Stress、Boss 等场景必须显式版本化，禁止把不同压力分布的成绩直接拼成同一排行榜。

## Simulation Protocol 版本

### Protocol V1 · 0.6.x 及以前

上游引擎在结构化动作被拒绝时不会推进模拟时间，而旧 Arena / CLI Battle 直接进入下一次 planner round。因此出现无效动作的局可能比名义预算少经历少量城市时间，例如 15 分钟实验实际结束于 14.98 分钟。

这不会让旧结果“失效”，但意味着它们只能与同样使用 Protocol V1 的实验直接比较。

### Protocol V2 · 0.7.0 起

拒绝的 planner 动作仍记录为 invalid，但该轮随后以 `noop` 消耗同一个固定 `dt`。除非 Game Over，算法每一轮都承担完全相同的城市时间，因此固定预算不再被无效动作悄悄缩短。

Protocol V2 同时引入时间加权网络健康指标，包括平均候车人数、passenger waiting seconds、峰值单站队列、全网候车峰值、车队平均载客率和动作稳定性。后续新冠军评估默认使用 Protocol V2 或更高版本。

# 实验记录

## Greedy Planner V1

- **ID**：`greedy-v1`
- **状态**：`baseline`
- **首次进入仓库**：0.1.x
- **核心思路**：
  - 开局按几何距离建立短线路骨架；
  - 新站以最小额外绕行代价插入已有线路；
  - 空线路优先分配机车；
  - 高压力线路优先增加机车与车厢；
  - 通过拓扑冷却避免频繁重画线路。
- **优点**：透明、稳定、计算成本低、容易复现和调试。
- **缺点**：明显短视，只优化局部几何代价和即时拥堵；缺少站型稀缺性、换乘价值、线路均衡和未来客流预测。
- **当前作用**：作为所有后续算法的第一基线。
- **淘汰条件**：新算法在扩大后的固定 Seed 集上稳定提高均值，同时不能显著恶化最差局和 Game Over 率。

## Balanced Greedy V2 · 首次挑战

- **ID**：`balanced-greedy-v2`
- **版本**：`2.0-candidate`
- **状态**：`candidate`
- **实现 PR**：#5
- **对战基线**：`greedy-v1`
- **Simulation Protocol**：`V1`
- **Benchmark Scenario**：`classic-v1`（上游原始推进逻辑）
- **固定 Seeds**：`42, 314, 2026, 4096, 65537`
- **步长**：100 ms
- **正式预算**：每个算法 × 每个 Seed 最多 15 分钟名义模拟预算
- **核心思路**：
  - 开局不仅考虑距离，还优先覆盖不同站型；
  - 新站插入评分同时考虑额外绕行、线路长度、线路客流压力和站型多样性；
  - 当已有线路过长且仍有可用线路槽位时，允许另开分流线路；
  - 机车和车厢扩容从固定绝对阈值改为结合网络平均压力的相对判断；
  - 拓扑调整冷却从 700 ms 提高到 900 ms，减少频繁改线。

### Protocol V1 · 15 分钟固定 Seed 结果

| Seed | Greedy V1 | Balanced V2 | 差值 |
| ---: | ---: | ---: | ---: |
| 42 | 38 | 38 | 0 |
| 314 | 42 | 42 | 0 |
| 2026 | 42 | 42 | 0 |
| 4096 | 35 | 35 | 0 |
| 65537 | 35 | 37 | +2 |

| 指标 | Greedy V1 | Balanced V2 |
| --- | ---: | ---: |
| 平均运送量 | 38.40 | **38.80** |
| 中位数 | 38.00 | 38.00 |
| 最低 | 35 | 35 |
| 最高 | 42 | 42 |
| Game Over 率 | 0% | 0% |
| 无效动作 | 21 | **16** |

### 辅助短局证据

在相同 5 个 Seeds、每局 5 分钟的 Protocol V1 预赛中：

- Greedy V1 平均 11.80；
- Balanced V2 平均 12.00；
- V2 同样只在少量局面建立微弱优势，但无效动作从 21 次降到 16 次。

### Protocol V1 结论

V2 在首轮 15 分钟实验中平均运送量提高约 **1.0%**，并减少约 **23.8%** 的无效动作；5 个 Seed 中有 4 个完全打平，仅在 Seed `65537` 上以 37:35 拉开差距。

这说明多目标均衡方向**没有造成回退，并表现出更好的动作稳定性**，但证据远不足以宣布新冠军。V2 因此只以 `candidate` 身份进入算法库，Greedy V1 继续保持默认 baseline。

## Protocol V2 基线重跑 · 0.7.0

为消除 rejected action 不走时带来的预算偏差，在 PR #8 / 0.7.0 中使用相同 Seeds、100 ms 步长、15 分钟预算重新执行 `classic-v1`。

这一次所有未 Game Over 的 episode 都**精确运行到 15.00 分钟**。旧 Protocol V1 中 Seed 314 / 4096 出现的约 14.98 分钟偏差被消除。

### Protocol V2 逐 Seed

| Seed | Greedy V1 | Balanced V2 | V1 均候车 | V2 均候车 | V1 invalid | V2 invalid |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 42 | 38 | 38 | 0.26 | 0.26 | 0 | 0 |
| 314 | 42 | 42 | 0.45 | 0.45 | 11 | 9 |
| 2026 | 42 | 42 | 0.34 | 0.34 | 0 | 0 |
| 4096 | 35 | 35 | 0.29 | **0.25** | 10 | **7** |
| 65537 | 35 | **37** | 0.53 | **0.43** | 0 | 0 |

### Protocol V2 汇总

| 指标 | Greedy V1 | Balanced V2 |
| --- | ---: | ---: |
| 平均运送量 | 38.40 | **38.80** |
| deliveries / min | 2.56 | **2.59** |
| 时间加权平均候车人数 | 0.37 | **0.35** |
| 平均单站峰值队列 | 1.00 | 1.00 |
| 时间加权车队载客率 | 5.8% | 5.2% |
| Game Over 率 | 0% | 0% |
| invalid action rate | 55.3% | **48.5%** |

### Protocol V2 结论

1. **比赛结论没有被协议修正翻转。** 这组 Seeds 上 deliveries 与 Protocol V1 完全一致，V2 仍是 38.80 vs 38.40 的小幅领先。
2. **时间公平性真正修复。** 无效动作不再让算法少经历城市时间，15 分钟就是 15 分钟。
3. **Balanced V2 仍不升冠军。** 5 个 Seeds 太少，而且绝大部分局面仍然打平。它继续保持 `candidate`。
4. **两个启发式算法的 invalid action rate 都偏高。** 这说明 planner 会重复尝试引擎拒绝的结构化动作，是下一轮算法工程需要直接消灭的浪费。
5. **更重要的是，`classic-v1` 在 15 分钟内压力过低。** 平均单站峰值只有 1，平均候车人数远低于 1，几乎没有形成真正的拥堵危机。这个场景适合做历史兼容基线，却不足以区分更强算法的上限。

因此下一阶段不会偷偷改写 Classic，而会新增**显式版本化 Stress Scenario**，把浏览器已经验证的动态站点压力机制抽成可复现 benchmark profile。Classic 留作历史基线，Stress 负责真正把算法逼出差异。

**Balanced V2 当前状态：继续研究，仍为 `candidate`。**

> 历史记录只追加和修正事实，不因算法被淘汰而删除。
